# 邮件场景全景地图与功能规划

> 配套文档：[STRATEGY.zh-CN.md](STRATEGY.zh-CN.md)（赛道与定位）、[SECURITY.md](../SECURITY.md)（安全模型）
> 本文回答一个问题：把「大家用邮件」的场景覆盖到足够全，每个环节该做什么工具。
> 人群基准：师生个人 + 学生组织（社团 / 部门 / 辅导员条线）双线。

---

## 一、场景全景地图

邮件使用可拆为六个生命周期环节。先看两类人群各自的真实场景，再看现状覆盖度。

### 1.1 师生个人场景

| 环节 | 真实场景 | 现状 |
|---|---|---|
| ✉️ 写 | 单封起草、润色、中英互译、语气调整 | Agent 对话天然覆盖，无需专工具 |
| 📤 发 | 单发、批量个性化（求职跟进、论文催稿、活动通知） | 批量已覆盖（`office_mail_preview/send`）；单发走对话即可 |
| 📥 收 | 教务/学院通知、导师邮件、笔试面试通知、论文录用进度、arXiv 与订阅日报 | **空白**：靠手动开邮箱刷未读，通知邮件易被订阅类淹没 |
| ↩️ 回 | 导师邮件须及时回、HR 邮件有时限、滞后跟进（投递无回音要礼貌催一次） | **空白** |
| 🗄️ 归档 | 成绩单/offer/发票等附件留存、申请材料翻找、半年前的邮件记录检索 | **空白**：搜索靠网页邮箱自带搜索，附件散落 |
| 📊 分析 | 求职申请台账（投了哪些、走到哪一步）、与导师/合作者往来频率 | **空白**：靠手动记 Excel |

### 1.2 学生组织场景（社团 / 部门 / 辅导员条线）

| 环节 | 真实场景 | 现状 |
|---|---|---|
| ✉️ 写 | 通知、感谢信、外联函、邀请函 | `office_docgen` + `office_template` 已覆盖文档侧 |
| 📤 发 | 纳新通知（几百封）、评奖通知、周报催收、校友邀请 | 批量已覆盖；退订链接与分批定时在策略文档列为 P1 |
| 📥 收 | **公邮收件**：报名申请、活动场地申请、外联来函、成员请假；假期无人管，开学堆积数百封 | **空白**：公邮箱是组织最痛的场景，谁接手谁头疼 |
| ↩️ 回 | 报名确认回执、外联答复、请假审批 | **空白** |
| 🗄️ 归档 | 报名表附件批量收取（简历、作品集）、活动材料归档交接 | **空白**：每届交接时材料散落各人邮箱 |
| 📊 分析 | 报名人数统计、通知触达情况、外联往来记录 | **空白** |

### 1.3 覆盖度结论

六个环节中，写与发已被现有六工具基本覆盖；**收、归档、分析三个环节全部空白**，且恰好都是「数据在邮箱里、动作在本地」的场景，与套件「本地运行、开放协议」的定位完全同构。回复与跟进依赖收件侧先落地，排其后。

## 二、优先环节功能规划

### 2.1 📥 收件分诊（P0：`office_inbox`）

核心洞察：收件摘要分诊是 Copilot 留存最高的能力，但巨头只能应用内被动响应；DSH 的定时任务可以做「每天早上 8 点自动分诊昨晚收件」的事件驱动形态，这是结构差异带来的独占位。

| 子工具 | 功能 | 设计要点 |
|---|---|---|
| `office_inbox_fetch` | IMAP 拉取最近 N 封的信封与正文摘要（时间/发件人/主题/正文前几百字/附件清单） | 默认只读；凭据走 `DSH_IMAP_PASS` 环境变量；QQ/163/Gmail/教育邮箱预设 IMAP 服务器 |
| `office_inbox_triage` | 输出结构化分诊结果：待办（有时限）/ 通知（知悉即可）/ 订阅（可清理）/ 私信（个人往来） | 分类规则分两层：确定性规则（发件人域、关键词）打底 + agent 语义判断补充；插件只出结构化数据，语义归纳由 agent 完成 |
| `office_inbox_clean` | 汇总全部订阅类发件人及其频率，生成退订建议清单 | **只出建议清单**；任何删除/移动操作必须逐条显式确认，绝不做批量静默清理 |

分诊数据落本地索引（见 2.2），后续所有工具共享这一份底层数据。

### 2.2 🗄️ 归档与检索（P1：`office_archive`）

| 子工具 | 功能 | 设计要点 |
|---|---|---|
| `office_archive_export` | 按时间/发件人/主题筛选批量导出 `.eml` + 生成索引文件 | 组织交接场景：一届的材料打包成目录树交接给下一届 |
| `office_archive_attach` | 批量下载附件到本地目录（报名表收取的核心动作） | 沿用路径边界护栏：只写用户指定目录，拒绝覆盖；文件名去重规则（发件人+主题+序号） |
| `office_archive_search` | 本地索引检索：按人、主题关键词、时间段、有无附件查邮件 | 索引为 JSONL（`~/.dsh/office/mail/index.jsonl`），每次 fetch 增量追加，不存全文只存元数据与摘要 |

学生组织的典型链路：`office_inbox_fetch` 拉取报名期全部收件 → `office_archive_attach` 把简历作品集批量落到本地 → `office_sheet` 做报名统计。三个工具串成「公邮收取一条龙」。

### 2.3 📊 数据分析（P1：`office_stats`）

| 子工具 | 功能 | 设计要点 |
|---|---|---|
| `office_stats_overview` | 收发总览：top 联系人、月度趋势、回复率 | 数据源两处：`sent-log.jsonl`（已发的审计日志）+ 收件索引；纯本地统计，零网络请求 |
| `office_stats_track` | 求职申请台账：按公司维度跟踪「已投 / 笔试 / 面试 / offer / 挂」 | 状态由分诊结果自动更新（识别笔试/面试通知邮件）+ 手动命令修正；输出可直接喂给 `office_sheet` 出统计表 |

边界：发送侧的打开率、点击率需要 tracking pixel 与退信解析，那是 Listmonk 类营销平台的领地，本套件不做（与策略文档既有结论一致）。分析全部基于本地已有数据。

### 2.4 ↩️ 回复与跟进（P2，暂缓）

依赖收件侧落地后才有数据。预留两个方向：跟进提醒（分诊标记「已投未回 N 天」的条目定期提示）与回复草稿（基于来信上下文生成草稿走现有发送管线）。等 `office_inbox` 跑稳后按需启动。

## 三、技术选型

| 项 | 选择 | 依据 |
|---|---|---|
| IMAP 库 | ImapFlow 1.4.1 | MIT 协议；2026-06 仍活跃发版；nodemailer 同作者（Postal Systems），与现有 SMTP 链路同源；自动处理 IMAP 扩展、支持流式拉取大邮箱；EmailEngine 的生产级引擎 |
| MIME 解析 | mailparser 3.7 | ImapFlow 同作者（Postal Systems），配套的事实标准：RFC2047 主题解码、multipart 正文提取、附件元数据 |
| 拉取方式 | 按需 fetch | DSH 是对话式运行时，用户问到才拉；IDLE 长连接监听属服务端形态，不在插件职责内 |
| 索引存储 | JSONL 追加 | 与 sent-log 同模式；无数据库依赖；单文件可 grep 可审计 |
| 凭据 | `DSH_IMAP_PASS` 环境变量 | 与 `DSH_SMTP_PASS` 同模式，不落配置文件 |

各邮箱 IMAP 预设：QQ（imap.qq.com:993）、163（imap.163.com:993）、Gmail（imap.gmail.com:993）、Outlook（outlook.office365.com:993）；教育邮箱手动填服务器地址。

## 四、明确不做的事

| 不做 | 原因 |
|---|---|
| 打开率 / 点击率跟踪 | 需要 tracking pixel 与退信解析，属营销平台领地（Listmonk/Mautic 已占） |
| 线索评分、营销漏斗 | 同上，撞 Mautic 主场 |
| 静默批量删除邮件 | 破坏性操作，永久坚持「只出建议 + 逐条确认」 |
| 收件全文落盘建全文索引 | 隐私敏感；只存元数据与短摘要，全文按需即时拉取 |
| IDLE 实时推送 | 属常驻服务形态，超出 DSH 插件职责边界 |

## 五、路线图整合

| 版本 | 内容 | 状态 |
|---|---|---|
| v1.2 | `office_inbox_fetch` / `office_inbox_triage`：收件分诊闭环 | **已上线**（71 项测试含 25 项 inbox 专项；真实邮箱端到端验证待用户配置 IMAP 授权码） |
| v1.3 | `office_archive` 三件套：导出 / 附件收取 / 本地检索 | 设计已定 |
| v1.4 | `office_stats` 两件套：往来总览 / 求职台账 | 设计已定 |
| v1.5 | `office_inbox_clean` 订阅清理（建议清单 + 逐条确认） | 依赖 v1.2 的订阅分类数据积累（triage 已输出 subscriptionSenders 频率表） |
| 远期 | 回复草稿与跟进提醒 | 视 v1.2 使用反馈决定 |

一句话总结：写与发已经立住，接下来三个版本把「收、归档、分析」补齐，邮件六个生命周期环节全部覆盖，师生个人与学生组织两条场景线各自形成完整闭环。
